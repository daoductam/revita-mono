## 1. Mục tiêu

Tài liệu này mô tả đầy đủ contract backend cần được bảo toàn hoặc bổ sung khi chuyển đổi từ `revita-be` (NestJS) sang `spring-revita-be` (Spring Boot).

Phạm vi gồm:

- HTTP REST API hiện có trong NestJS.
- Các API mà frontend đang gọi nhưng NestJS chưa khai báo.
- WebSocket/Socket.IO namespace và event.
- Authentication, RBAC, integration bên ngoài và yêu cầu vận hành.
- Định hướng chia module trong Spring Boot.

> Tài liệu này là artifact discovery/spec của workflow `.agents`. Chưa có code backend nào được thay đổi.

## 2. Hiện trạng

### 2.1. `revita-be`

- NestJS backend.
- Global prefix: `/api` cho các HTTP endpoint.
- Swagger UI: `/docs`.
- Có 294 HTTP route thực tế từ các controller.
- Có 5 Socket.IO namespace.
- Sử dụng PostgreSQL/Prisma, MongoDB, Redis, Supabase, PayOS, Google OAuth2, AWS SNS, Resend, Gemini và FastAPI.

### 2.2. `spring-revita-be`

- Hiện mới có `SpringRevitaBeApplication`.
- Chưa có controller/service/repository/entity/security configuration.
- `pom.xml` mới có `spring-boot-starter` và test starter.
- Chưa có HTTP API hoặc WebSocket API tương đương.

### 2.3. Quy ước path và versioning

Trong danh sách dưới đây:

- NestJS `:id` tương đương Spring `{id}`.
- `/api/v1` là canonical path của Spring Boot cho toàn bộ business API mới.
- `/api` là legacy compatibility path để frontend/desktop hiện tại không phải sửa ngay; route này phải đi qua cùng application service với `/api/v1`, không được nhân đôi business logic.
- Với route Nest có dạng `/api/<suffix>`, route canonical Spring tương ứng là `/api/v1/<suffix>`; bản `/api/<suffix>` chỉ là alias tương thích trong phase 1.
- 24 route chỉ xuất hiện ở frontend/desktop phải có quyết định mapping riêng sang `/api/v1`; không tự suy đoán payload hoặc semantics chỉ từ tên path.
- `GET /` là route đặc biệt không có `/api` trong NestJS.
- Các route Swagger/Actuator là operational endpoint, không tính vào 294 business endpoint.

## 8. Contract response đề xuất cho Spring

Để frontend, desktop và mobile dễ migrate, nên thống nhất response:

```json
{
  "data": {},
  "meta": {
    "requestId": "req_xxx"
  }
}
```

List response:

```json
{
  "data": [],
  "meta": {
    "page": 1,
    "limit": 20,
    "total": 100,
    "totalPages": 5,
    "requestId": "req_xxx"
  }
}
```

Error response:

```json
{
  "error": {
    "code": "validation_error",
    "message": "Invalid request parameters",
    "details": [],
    "requestId": "req_xxx"
  }
}
```

Status code tối thiểu:

```text
200 OK
201 Created
204 No Content
400 Bad Request
401 Unauthorized
403 Forbidden
404 Not Found
409 Conflict
422 Unprocessable Entity
429 Too Many Requests
500 Internal Server Error
```

Hiện frontend đang trộn nhiều kiểu pagination: `page/limit`, `limit/offset` và `skip`. Nên giữ compatibility ở phase đầu, sau đó chuẩn hóa theo từng module.

Các envelope ở mục này là **contract đề xuất cho Spring**, chưa phải response snapshot đã được kiểm chứng từ NestJS. Trước khi code migration cần lập thêm bảng request/response thực tế theo từng route, gồm DTO/body, query/path params, status code, content type và lỗi.

## 9. Operational endpoints nên bổ sung

```text
GET /actuator/health
GET /actuator/info
GET /swagger-ui/index.html

```

Nest có exclude `/health` trong bootstrap nhưng hiện chưa có health controller thực sự. Spring nên bổ sung health check cho PostgreSQL, MongoDB, Redis và các integration quan trọng.

## 10. Integration bên ngoài

Spring backend cần thay thế các integration sau:

- PostgreSQL/JPA hoặc jOOQ cho dữ liệu nghiệp vụ.

## 17. Quyết định migration áp dụng — Compatibility-first

Theo recommendation đã chọn, phase đầu sẽ coi Spring Boot là **drop-in replacement** cho NestJS; frontend và desktop hiện tại chưa bắt buộc phải sửa.

### 17.1. Compatibility policy

1. Giữ nguyên 294 HTTP route baseline trong mục 3 như legacy source contract; mỗi route được expose canonical trên `/api/v1/...`.
2. Spring cung cấp thêm 24 compatibility route đang được frontend/desktop khai báo hoặc gọi ở mục 4, sau khi chốt mapping sang canonical v1 service/route.
3. Giữ nguyên HTTP method, request content type, response shape, pagination và status code của client trên `/api`; `/api` là alias legacy trỏ vào cùng behavior với `/api/v1`.
4. Các response envelope mới ở mục 8 chỉ là mục tiêu phase sau; không áp dụng global trong phase 1 nếu làm thay đổi payload legacy.
5. Giữ Socket.IO, 5 namespace và event name hiện tại. Chưa chuyển sang STOMP trong phase 1.
6. Route alias phải có owner, test và kế hoạch deprecation; không xóa alias trước khi toàn bộ client chuyển sang route canonical.
7. `GET /`, Swagger, OpenAPI và Actuator không bị ép vào `/api/v1`; đây là root/operational endpoints.
8. Các route source đang `@Public` hoặc không có guard nhưng làm thay đổi queue, clinical hoặc payment state không được port thành public Spring mutation; phải có JWT/role hoặc scoped internal credential trước cutover.
9. Flyway là migration tool cho schema do Spring sở hữu; Prisma migration history chỉ là baseline source, không replay mù trên database đã có dữ liệu.

### 17.2. Security policy

Compatibility không có nghĩa là giữ lại lỗi bảo mật. Trước production cutover bắt buộc:

- Không dùng fallback JWT secret; thiếu secret phải làm application fail fast.
- CORS chuyển từ `origin: true` sang allowlist theo môi trường.
- Mọi route staff/admin và resource route phải có JWT, role và ownership rule rõ ràng.
- Giữ behavior response cần thiết cho client nhưng chuẩn hóa error nội bộ, audit log và rate limit.

### 17.3. Cutover policy

- Chỉ chuyển traffic sau khi contract test chạy qua cả web và desktop.
- Cho phép rollback bằng cách đổi `API_BASE_URL`/routing về NestJS.
- Không chạy dual-write nghiệp vụ nếu chưa có mapping và reconciliation; database migration phải backward-compatible.

Đây là quyết định phạm vi cho implementation plan, không phải yêu cầu refactor toàn bộ frontend trong phase đầu.
